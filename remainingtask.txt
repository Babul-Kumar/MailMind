# BUG FIX: MAILMIND MISCLASSIFIES ACTIONABLE ANNOUNCEMENTS AS P3

## Observed issue

The production MailMind inbox classifies these emails as P3 · Routine:

- "October 2026 NPTEL Exams - Hall Tickets Released!!"
- "FINAL October 2026 NPTEL Exams – Hall Tickets, Centre Details and Registration..."
- "Exam Format - October, 2026!!"

The hall-ticket announcement explains that registered candidates can download their exam hall tickets.

These messages may require a meaningful user action, but the current application does not adequately surface that action.

## Objective

Find the root cause and improve MailMind's general email understanding so actionable announcements are recognized across different senders, subjects, and domains.

Do not implement a special case for NPTEL, hall tickets, admit cards, or any specific subject line.

## 1. Trace the existing classification pipeline

Inspect the actual production code and determine:

- Which model and preprocessing pipeline generate P3.
- Whether the displayed priority comes directly from the model or from a later mapping, threshold, or cached result.
- Whether the full email body is available during classification.
- Whether HTML parsing, MIME decoding, or truncation removes important context.
- Whether the actionability layer runs independently of priority classification.
- Whether Needs Attention filters out P3 messages before actionability is evaluated.
- Whether cached results were produced by older logic.
- Whether frontend fields accurately reflect backend outputs.

Reproduce the issue using the actual message content or a privacy-safe representative fixture.

Record the original model output and the downstream filtering behavior separately.

## 2. Preserve the frozen production model

Do not retrain, replace, or modify the frozen production model or its artifacts.

Frozen model SHA-256:

8524ad73965859ee022f1271caee0040928e7805ab7d32c49b2f26e994f98c06

Do not force these messages into P1 or P2 merely to make them visible.

If the model correctly identifies them as routine informational messages according to its learned labels, retain that classification and improve the separate actionability representation.

The product must distinguish:

- Priority classification.
- Actionability.
- Urgency.
- Applicability.
- Deadline status.

An email can be P3 and still contain an action worth surfacing.

## 3. Improve general action-intent detection

Inspect and improve the existing actionability pipeline.

It should recognize announcements that imply an action, not just messages that explicitly say "you must do this."

Examples include:

- Documents or tickets becoming available for download.
- Applications opening or closing.
- Registration steps.
- Assignment submissions.
- Account verification.
- Payment or renewal actions.
- Appointments requiring preparation.
- Requests for responses.
- Security actions.

Use the complete available message content, relevant metadata, and existing NLP capabilities.

Do not add sender-specific rules or subject-keyword exceptions.

Do not assume that every recipient is eligible for an announced action.

For the hall-ticket example, the expected interpretation is:

Action: Download the October 2026 exam hall ticket.

Reason: The announcement states that hall tickets have been released.

Applicability: Relevant to candidates registered for the examination.

Next step: Open the original email and download the ticket if registered.

Deadline: Unknown unless reliably established from the email.

This is a test expectation, not a hardcoded response.

## 4. Fix the downstream Needs Attention policy

Determine why a P3 message with an actionable intent does not reach Needs Attention.

If the current pipeline filters by priority before evaluating actionability, correct the ordering.

Use a separate actionability score or structured result, with confidence and an explanation where supported.

Allow an actionable P3 email to enter Needs Attention when justified, without altering its P3 classification.

Do not promote every P3 announcement. Routine newsletters, general course updates, feedback forms, and informational emails must remain out of the active queue unless they contain a meaningful action.

Respect the existing 8-day age policy, Older actions section, resolution state, snooze state, and critical-item rules.

## 5. Correct cache invalidation

If the actionability logic changes, inspect whether cached emails contain stale actionability results.

Invalidate or version only the affected derived metadata as appropriate.

Do not reclassify the entire mailbox unnecessarily.

Do not overwrite user resolution or snooze state.

Do not cause repeated scans to create duplicate tasks.

## 6. Add regression tests

Create representative tests for:

1. An actionable hall-ticket announcement classified P3.
2. A registration announcement with a genuine action.
3. A routine feedback form without an actionable requirement.
4. A general informational course announcement.
5. A P3 email containing a meaningful upcoming deadline.
6. A message whose applicability to the recipient is uncertain.
7. An old actionable announcement that belongs in Older actions.
8. An expired action that no longer belongs in active attention.
